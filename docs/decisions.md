### Step 4 (2026-10-10)
- Evidence modules are **supervised** (use the domain flags on train), selected on val among logistic regression and gradient boosting by average precision (scenarios: HGB depth 3 for both domains; battledim infra: logistic regression C=0.1), isotonic calibration on val, with val numbers cross-fitted over 4 time blocks. The baselines are unsupervised, so the val-F1 comparison favours the modules by construction; it shows what labelled training buys, not that the method is better than unsupervised detection. Say so in the paper.
- Val event F1 (module vs best baseline): battledim infra 0.857 vs 0.560; scenarios infra 0.893 vs 0.730; scenarios quality 0.771 vs 0.261 (all modules >= baseline, no explanation needed).

- Evidence probabilities are stored only for val (cross-fitted) and test rows (`data/processed/evidence_*.parquet`); train rows are NaN because they are in-sample for the base model. Fusion (Step 5) is therefore tuned on val only.

### Step 5 (2026-10-10)
- **Selection:** validation macro-F1 (out-of-fold over 4 time blocks, scenarios): F-A 0.540, F-B 0.645 -> **F-B selected** (rule: best validation macro-F1; ties within 0.005 go to F-B). Test numbers are in `results/tables/fusion_ablation.md`.
- F-B first used argmax of the pignistic probabilities; this made temporal reliability irrelevant (the sign of the N-vs-I margin depends only on p). It was changed to a discounted-belief decision `r*p >= gamma` after seeing validation and test output of the first version, and not changed afterwards. Disclose this in the paper.
- **Honest outcome (scenarios, test):** the fusion designs reach higher point-level macro-F1 (F-B 0.571, F-A 0.570) than threshold voting (0.433), the single joint model (0.321) and the baselines (0.364 and 0.247), but they have **much lower event-level precision and many more false alarms** (F-B event F1 0.359, 2.19 false alarms/day) than simple threshold voting on the same evidence (event F1 0.840, 0.16 false alarms/day). The macro-F1 selection objective rewards minority-class recall and was not tuned for false alarms. Temporal features help a little (F-A macro-F1 0.570 vs 0.508 without; F-B 0.571 vs 0.566), within the noise of 60 test events.
- **BattLeDIM (infrastructure only, 8 test events):** F-B event F1 0.897 vs voting 0.941; few events and a drifting background, so not evidence for the method.
- Recurrence counts evidence flicker as separate episodes (for example 12 episodes in 7 days on drifting background), so it is a weak signal in this data.
- Fusion is fitted on validation only (evidence probabilities on train are in-sample). The joint-model and baseline ablations are refit on train as in Steps 3 and 4.

### Step 6 (2026-10-10)

### Pre-freeze review and the changes it caused (2026-10-10; validation data only, nothing frozen, no test evaluation)
A read-only review of the final-evaluation code ran before the freeze (six reviewers; five reported, 31 findings; the crash-safety reviewer and most verifiers hit the session limit, so I checked every finding myself). The rework below followed. The plan for it was approved by the user in plan mode.

**Correction.** An earlier line said test_v3 "has never been opened". That was inaccurate: my first dry run of `run_final.py` loaded the `scenarios_v3` file, test rows included, and computed features over it (loaded and featurised once before the freeze). Only validation rows were passed to any model or metric, and no number from the test rows was produced or seen. **User decision:** test_v3 stays the headline set, with this stated wherever the set is described. The dry run and the preflight now read validation rows from the `scenarios` file (identical rows) and no held-out file at all; `load_dataset` refuses a held-out set until the freeze verifies.

**User decision: event-counted F1 is the tuned objective and the verdict metric.** The Round-1 event precision is true alert segments / all segments, so an event whose alert drops out for more than 1 h contributes several true segments. On validation the tuned rules had about 2.8 true segments per detected event, and F-B fragments more than voting by construction (a dip below 0.5 resets its persistence), which could tilt the comparison. Event-counted precision = detected events / (detected events + false alarms). The objective is now: maximise out-of-fold event-counted F1 subject to at most 0.5 false alarms per day, for the fusion rules, threshold voting and the baselines alike. The segment-based F1 is still reported in every table.

Other changes (my decisions, approved with the plan):
- **Category accuracy rule.** Old: the most frequent non-Normal category inside the event window equals the event category. That marks a prediction equal to the row labels wrong on about two thirds of Combined events (their quality part is much shorter than the infrastructure part). New: an event is category-correct when the set of streams the model reports during the event equals the streams the event contains; an undetected event is wrong. A prediction equal to the labels scores 1.0 (unit test). Round-1 tables keep the old rule and are not comparable.
- **Tie-break.** Exact ties on the objective go to the setting that alerts on fewer rows. Before, the first grid point won, which was the most permissive threshold.
- **Bootstrap.** Events are resampled for recall, precision, F1 and category accuracy (true segments stay with their event) and whole days for false alarms, as R6 asks. The same draws are used for every model on a set, so paired differences exist.
- **Verdict rule, frozen.** Fusion beats voting only if the 95% interval of the paired difference in event-counted F1 is entirely above 0 and fusion is within the cap on that test set. Worse if entirely below 0. Otherwise no detectable difference. The rule is in hashed code and in the frozen configuration.
- **BattLeDIM label leak removed.** Round 1 set p_infra to missing on the label-derived `ambiguous` rows before computing temporal features, so those features depended on where true leak windows ended. Round 2 predicts on every row with valid features and applies `ambiguous` only when scoring. On the rows Round 1 scored the probabilities are identical (maximum difference 0.0).
- **Final run in two phases.** Phase A opens a test set for one model, stores its per-row predictions at once and marks the log entry completed. Phase B computes every number from the stored predictions and can be repeated without opening anything. A model opened in an interrupted run is reported as interrupted and not re-opened unless `--retry-interrupted` is given, which is logged as a second access. Predictions are kept in `results/round2/predictions/`.
- **Freeze hardened.** It refuses a tree with uncommitted inputs, refuses to be rebuilt after any held-out access, requires that the tuned parameters were produced by the code and data on disk, re-derives its parameter blocks in `verify()`, and hashes text files independently of line endings. Feature caches are trusted only if built from the current raw file, feature code and split file.
- **Reporting.** Latency p90, per-event-type detection, row-level alert precision and recall, segment counts, alert-time shares in the validation tables, a baseline table that says which baselines could not meet the cap, and a note that a zero-width interval is not certainty.

Not changed: the alert-duration weakness of the event metrics (reported through the alert-time columns; the user's objective has no duration term). On BattLeDIM validation every tuned rule alerts on 76% to 100% of rows, so BattLeDIM event scores carry little information.

The honest reading is that the effect of temporal features on event F1 is small and not stable in sign; their consistent effect is on category accuracy.
- **Baselines.** The fixed-threshold baseline reaches event F1 0.637 [0.528, 0.739] at 0.06 false alarms per day on test_v3, close to the 0.667 of voting, but its category accuracy is 0.400. Isolation Forest (0.317, 0.57 per day) and One-Class SVM (0.328, 0.71 per day) are above the cap on test. The single joint model alerts on 59% of rows (0.269, 1.13 per day).
- **Detection is slow and partial at the tuned thresholds:** F-B first alerts a median of 3.4 h after an event starts (90th percentile 25 h) and alerts on 22% of the rows inside events.
- **BattLeDIM test (exposed, 8 events) says nothing:** F-B, both no-temporal variants and voting alert on 100% of rows and score the same 0.941; F-A alerts on 50% of rows and scores 0.258. This is the alert-duration weakness of the objective, not detection quality.

Reframing, as the plan asks when fusion does not win on event F1: on this evidence the value of the fusion layer is not better detection. It is (a) naming the right streams for an event, where it is detectably better than voting on every scenario set, and (b) the priority and the explanation it attaches. Detection itself comes from the calibrated evidence modules and a strict threshold.
