### Step 2 (2026-10-10)
- **Two evaluation datasets, reported separately:** (a) `battledim_network`: real leak labels on simulated data, infra signals only (flow = PUMP_1, pressure = mean of 33 sensors), 33 events; (b) `scenarios`: semi-synthetic, 3 nodes, 180 events, all 4 signals. There is no labelled real quality data, so quality is only evaluated on scenarios (real USGS background, injected events).

### Step 3 (2026-10-10)

One-Class SVM from CLAUDE.md not implemented (PLAN Step 3 lists only the two; OCSVM on ~400k rows is slow). Add later if wanted.

Rows that are invalid, ambiguous or lack features are not scored.
- Domain evaluation: infra detectors vs `infra_flag`, quality detectors vs `quality_flag`; the joint IF is scored against each. Combined events count in both domains.
- BattLeDIM test split has only 8 events (1 burst, 7 leaks); fixed thresholds detect all of them partly because the late-2019 background drifts and keeps alerting (event precision ~0.41). Read these numbers with care.

### Step 4 (2026-10-10)
- Evidence modules are **supervised** (use the domain flags on train), selected on val among logistic regression and gradient boosting by average precision (scenarios: HGB depth 3 for both domains; battledim infra: logistic regression C=0.1), isotonic calibration on val, with val numbers cross-fitted over 4 time blocks. The baselines are unsupervised, so the val-F1 comparison favours the modules by construction; it shows what labelled training buys, not that the method is better than unsupervised detection. Say so in the paper.
- Val event F1 (module vs best baseline): battledim infra 0.857 vs 0.560; scenarios infra 0.893 vs 0.730; scenarios quality 0.771 vs 0.261 (all modules >= baseline, no explanation needed).
- BattLeDIM infra calibration is poor (Brier val 0.28, test 0.33; only 17 train events and a drifting background). Reported as is.
- Temporal feature defaults (theta 0.5, k 3 steps, windows 2 h/6 h, gap 2 h, recurrence window 7 days) are fixed a priori, not tuned. Missing evidence counts as no evidence.
- Evidence probabilities are stored only for val (cross-fitted) and test rows (`data/processed/evidence_*.parquet`); train rows are NaN because they are in-sample for the base model. Fusion (Step 5) is therefore tuned on val only.

### Step 5 (2026-10-10)
- **Selection:** validation macro-F1 (out-of-fold over 4 time blocks, scenarios): F-A 0.540, F-B 0.645 -> **F-B selected** (rule: best validation macro-F1; ties within 0.005 go to F-B). Test numbers are in `results/tables/fusion_ablation.md`.
- F-B first used argmax of the pignistic probabilities; this made temporal reliability irrelevant (the sign of the N-vs-I margin depends only on p). It was changed to a discounted-belief decision `r*p >= gamma` after seeing validation and test output of the first version, and not changed afterwards. Disclose this in the paper.
- **Honest outcome (scenarios, test):** the fusion designs reach higher point-level macro-F1 (F-B 0.571, F-A 0.570) than threshold voting (0.433), the single joint model (0.321) and the baselines (0.364 and 0.247), but they have **much lower event-level precision and many more false alarms** (F-B event F1 0.359, 2.19 false alarms/day) than simple threshold voting on the same evidence (event F1 0.840, 0.16 false alarms/day). The macro-F1 selection objective rewards minority-class recall and was not tuned for false alarms. Temporal features help a little (F-A macro-F1 0.570 vs 0.508 without; F-B 0.571 vs 0.566), within the noise of 60 test events.
- **BattLeDIM (infrastructure only, 8 test events):** F-B event F1 0.897 vs voting 0.941; few events and a drifting background, so not evidence for the method.
- Recurrence counts evidence flicker as separate episodes (for example 12 episodes in 7 days on drifting background), so it is a weak signal in this data.
- Fusion is fitted on validation only (evidence probabilities on train are in-sample). The joint-model and baseline ablations are refit on train as in Steps 3 and 4.

### Step 6 (2026-10-10)
- Live nodes were rebuilt to match the training backgrounds (pressure = mean of a sensor group, one of 3 flow sensors, a USGS station with per-node time shifts) so the deployed scenario-trained modules see the same distributions. Step 1 check re-run and still passes.

### Pre-freeze review and the changes it caused (2026-10-10; validation data only, nothing frozen, no test evaluation)
A read-only review of the final-evaluation code ran before the freeze (six reviewers; five reported, 31 findings; the crash-safety reviewer and most verifiers hit the session limit, so I checked every finding myself). The rework below followed. The plan for it was approved by the user in plan mode.

**Correction.** An earlier line said test_v3 "has never been opened". That was inaccurate: my first dry run of `run_final.py` loaded the `scenarios_v3` file, test rows included, and computed features over it (loaded and featurised once before the freeze). Only validation rows were passed to any model or metric, and no number from the test rows was produced or seen. **User decision:** test_v3 stays the headline set, with this stated wherever the set is described. The dry run and the preflight now read validation rows from the `scenarios` file (identical rows) and no held-out file at all; `load_dataset` refuses a held-out set until the freeze verifies.

**User decision: event-counted F1 is the tuned objective and the verdict metric.** The Round-1 event precision is true alert segments / all segments, so an event whose alert drops out for more than 1 h contributes several true segments. On validation the tuned rules had about 2.8 true segments per detected event, and F-B fragments more than voting by construction (a dip below 0.5 resets its persistence), which could tilt the comparison. Event-counted precision = detected events / (detected events + false alarms). The objective is now: maximise out-of-fold event-counted F1 subject to at most 0.5 false alarms per day, for the fusion rules, threshold voting and the baselines alike. The segment-based F1 is still reported in every table.

Other changes (my decisions, approved with the plan):
- **Category accuracy rule.** Old: the most frequent non-Normal category inside the event window equals the event category. That marks a prediction equal to the row labels wrong on about two thirds of Combined events (their quality part is much shorter than the infrastructure part). New: an event is category-correct when the set of streams the model reports during the event equals the streams the event contains; an undetected event is wrong. A prediction equal to the labels scores 1.0 (unit test). Round-1 tables keep the old rule and are not comparable.
- **Tie-break.** Exact ties on the objective go to the setting that alerts on fewer rows. Before, the first grid point won, which was the most permissive threshold.
- **Bootstrap.** Events are resampled for recall, precision, F1 and category accuracy (true segments stay with their event) and whole days for false alarms, as R6 asks. The same draws are used for every model on a set, so paired differences exist.
- **Verdict rule, frozen.** Fusion beats voting only if the 95% interval of the paired difference in event-counted F1 is entirely above 0 and fusion is within the cap on that test set. Worse if entirely below 0. Otherwise no detectable difference. The rule is in hashed code and in the frozen configuration.
- **BattLeDIM label leak removed.** Round 1 set p_infra to missing on the label-derived `ambiguous` rows before computing temporal features, so those features depended on where true leak windows ended. Round 2 predicts on every row with valid features and applies `ambiguous` only when scoring. On the rows Round 1 scored the probabilities are identical (maximum difference 0.0).
- **Final run in two phases.** Phase A opens a test set for one model, stores its per-row predictions at once and marks the log entry completed. Phase B computes every number from the stored predictions and can be repeated without opening anything. A model opened in an interrupted run is reported as interrupted and not re-opened unless `--retry-interrupted` is given, which is logged as a second access. Predictions are kept in `results/round2/predictions/`.
- **Freeze hardened.** It refuses a tree with uncommitted inputs, refuses to be rebuilt after any held-out access, requires that the tuned parameters were produced by the code and data on disk, re-derives its parameter blocks in `verify()`, and hashes text files independently of line endings. Feature caches are trusted only if built from the current raw file, feature code and split file.
- **Reporting.** Latency p90, per-event-type detection, row-level alert precision and recall, segment counts, alert-time shares in the validation tables, a baseline table that says which baselines could not meet the cap, and a note that a zero-width interval is not certainty.

Not changed: the alert-duration weakness of the event metrics (reported through the alert-time columns; the user's objective has no duration term). On BattLeDIM validation every tuned rule alerts on 76% to 100% of rows, so BattLeDIM event scores carry little information.

- **BattLeDIM test (exposed, 8 events) says nothing:** F-B, both no-temporal variants and voting alert on 100% of rows and score the same 0.941; F-A alerts on 50% of rows and scores 0.258. This is the alert-duration weakness of the objective, not detection quality.

Reframing, as the plan asks when fusion does not win on event F1: on this evidence the value of the fusion layer is not better detection. It is (a) naming the right streams for an event, where it is detectably better than voting on every scenario set, and (b) the priority and the explanation it attaches. Detection itself comes from the calibrated evidence modules and a strict threshold.

### Design decisions
- **Rules before models.** Intent, ward and day are read by rules that work on English, Devanagari Hindi and Hindi in Latin letters. Why: the time of a tanker must not depend on a translation or a language model. The LLM is not used for understanding (the plan allowed it "only if rules fail"; a question the rules cannot place goes to the notice search or gets the no-information reply).
- **Schedule status is derived, not stored.** The CSV holds the planned slot and whether a delivery is planned as delayed; scheduled / en route / delivered / delayed follow from the replay clock, so an answer is always consistent with the time on the dashboard. Day offsets are relative to the current replay day (the schedule repeats every replay day).
- **Grounding guard has two halves.** (1) Nothing ungrounded: every time, date, ward number, ward name, tanker id, phone number, other number, day word and status word of an LLM answer must be in the retrieved records, and no cause word may appear. (2) Nothing missing: a schedule answer must state the time of every retrieved delivery, the status of delivered and delayed tankers and the possible-delay note; a status answer must state what the sensors show; a notice answer must share enough words with the notice. The second half was added when a test showed that an LLM answer with no checkable claim ("x", "I am not sure") passed the first half.
- **Notice search has a Hindi channel.** Each notice has a few Hindi keywords (Devanagari and Latin letters). A Hindi question is matched on them first (at least two shared words), and only then through its English translation. Why: on validation a translation slip ("tanker" -> "tank") sent a question to the wrong notice.
- **Hint words for speech recognition.** The recogniser gets the ward names and the loanwords "ward" and "tanker" in both scripts as hint words (`hotwords`). On the validation questions this lowered the Hindi word error rate from about 31% to about 15% and the English one from 5.6% to 1.4%. The rules also accept the spellings the recogniser still produces for "ward" and "tanker", and a ward name that is spelled almost like a known one; a name changed too much is not guessed, the citizen is asked for the ward.
- **The LLM's question for a Hindi schedule or status question is built from the understood ward and day** ("When is the next water tanker for Ward 4 (Bagayam)?"), not machine-translated. Why: on validation a mis-heard question, translated literally, made the LLM write a fluent wrong sentence.
- **Guard additions found on validation:** a schedule answer must name the ward and every tanker id; a notice answer must carry the times or numbers of at least one notice sentence completely, may not take half of a time range, and may not contain a negation that the notice does not have.
- **Validation was used several times** (rules, keywords, hint words, guard, prompt: five rounds of fixes on the 20 validation questions, which are now all answered correctly). That is what validation is for, and it is why only the single test run is reported as the result.
- **Hindi replies.** Schedule and status answers in Hindi are fixed Hindi sentences (no translation involved). Notices and accepted LLM answers are translated by the translation model, and the numbers must survive (a full hour may become a plain number); otherwise the Hindi fixed sentence, or for a notice the English text with a note, is sent.
- **Language of the reply:** the chat's `/language` setting if set, otherwise the language of the message (Devanagari or clear Hindi words in Latin letters -> Hindi; for voice the language the recogniser detected), otherwise Hindi. The plan said "default Hindi"; an English question is answered in English unless the chat asked for Hindi.
- **Voice reply only for a voice question.** A typed question gets text. The text of a voice answer starts with what was understood ("I heard: ..."), so a recognition error is visible to the citizen.
- **Backlog skipped.** Messages that were waiting before the bot started are not answered late.
- **Tickets:** a ticket stores the location, the time, the photo and what the sensors showed, and no chat id or name. The photo waiting for its location is kept in memory only (10 minutes). The dashboard gets a re-encoded small copy without metadata. Tickets live in the demo database, which `run_demo.py` clears at every start; the photo files stay in `data/citizen/uploads/` (git-ignored) until the user deletes them.
- **Only the test server makes a ticket without Telegram:** `scripts/e2e_server.py` adds one ticket from a generated picture (marked "test data") so that the browser tests have something to show.
- **Browser specs write into `results/` only through `scripts/screenshots.py`.** A plain `npx playwright test` had overwritten the stored Round 5 screenshots once in this round; they were restored from git, and the default output is now a scratch folder. The stored screenshots are still the Round 5 ones (they do not show the new Complaints link); the plan says not to regenerate them unless the user asks.
- **`scripts/check_telegram.py`:** its `.env.example` criterion required exactly the three alert settings; it now requires them to be present (the citizen settings were added to the same file).

### Evaluation (C6)
- **Protocol.** 60 questions written in this round (30 English, 30 Hindi, 5 of the Hindi ones in Latin letters), 20 validation and 40 test. Prompts, the retrieval threshold and the language rules were set with the validation questions only. Each part of the test (fixed sentences, local LLM, voice) ran once; raw outputs are stored in `results/citizen/test_outputs.json` and `scripts/citizen_eval.py` only recomputes tables from them afterwards.
- **Honest limits of this evaluation:** the questions were written by the developer, who knew the rules, so the result says how the system does on the intended kind of question, not on free citizen language; the schedule is fictional; the speech is synthetic (the questions were spoken by the same text-to-speech model that speaks the answers), which is cleaner than a real voice note; 20 questions per language.
- **Result, fixed sentences:** 98% of the test questions answered correctly (English 100%, Hindi 95%); wrong: hi-30.
- **Result, local LLM (`llama3.2:3b`):** of 36 questions given to the LLM, 23 answers broke a grounding rule and were replaced by the guard; 13 answers were finally written by the LLM; correct after the guard: 98%. The small model is weakest when several deliveries must be listed. The guard is what makes the LLM safe to use here; without it the wrong answers would have reached the citizen.
- **Result, voice:** word error rate 1.4% (English) and 23.5% (Hindi) on synthetic speech; correct from spoken question to spoken answer: 82%; median time 1.2 s on the laptop GPU, without Telegram transfer times.
- **What went wrong on the test questions (nothing was changed afterwards):**
  - Text, both writers: `hi-30` ("bijli ka bill kahan jama karein?", an electricity-bill question in romanised Hindi) was answered with the water-bill notice. The keyword search matched "bill" and "jama"; a lexical search cannot tell an out-of-scope bill from the water bill. One Hindi notice answer was sent in English with a note because the translation lost a number.
  - Local LLM: of the 23 replaced answers, 14 only left something out (a second delivery, the tanker id, the status), 6 stated a time, tanker, status or other fact that is not in the records, and 3 used a cause word. Two of the cause-word cases were the words "broken pipe" in an answer about how to report one: a false alarm of the word list, which errs on the safe side.
  - Voice: 7 of 40 spoken questions were not answered correctly, all because of what the recogniser wrote: `en-16` heard as "At what time will the tanker arrive in Bagayon tomorrow?"; `hi-13` heard as "वार्ड साथ का टैंकर आज ने थे क्या"; `hi-16` heard as "वार्ड नमबर दो के टैंकर की स्थिती बताईए"; `hi-17` heard as "आज वार्ड छेह में कौन सा टैंकर आ रहा है?"; `hi-22` heard as "गांधी नगर में अभी कोई तलट है क्या?"; `hi-24` heard as "हेतलाई नंबर क्या है?"; `hi-30` heard as "बिजरी का बिल कहां जमा करें". Number words written by ear ("साथ" for सात, "छेह" for छह), "alert" and "helpline" mis-heard, and one ward name. The English voice questions failed once (a ward name). These spellings were not added to the rules after the test; they are listed as the main thing to improve, together with real recordings.
  - With all models loaded, 6978 MB of the 8188 MB GPU memory were in use, so everything fits at once but with little room.
- **No real Telegram request** was made in Part A: the bot was exercised only through a stand-in for the Bot API in the tests. The first real conversation is the live test with the user.
