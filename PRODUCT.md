# Product

## Platform

web

## Users
- **Primary: a water-utility control-room operator** on shift, watching a distribution network of sensor points. Their job: notice when a point behaves unusually, tell an infrastructure problem (flow/pressure: leak, burst) from a water-quality problem (turbidity/TDS) or both, judge how urgent it is, and decide whom to send where. The dashboard is designed for this person first (user decision, 2026-10-18).
- **Secondary: residents of the served wards**, who never see the dashboard. They reach KAMI only through the Telegram bot (tanker schedule and notice questions in Hindi or English, by text or voice; photo + location reports of damaged pipes). Their reports appear to the operator on the Complaints page and as map markers.
- **Also present: the project's evaluators** (guide, faculty panel, paper reviewers). They see the operator interface during the live demo and must be able to trust every label on it; they are not the design target.

## Product Purpose
KAMI is an anomaly-intelligence system for water networks, built as a solo college project. It watches four signals per sensor point (flow, pressure, turbidity, TDS), scores infrastructure behaviour and water-quality behaviour as separate evidence streams, adds temporal context (how suddenly it started, how long it has lasted, how often it recurred), and fuses them into a category (Normal, Infrastructure, Quality, Combined), a priority, a confidence and a plain-language explanation. Success for the operator: the right node, the right kind of problem and an honest reason, early enough to act, with few false alarms. Success for the project: a working live system and evaluation results reported honestly, including where the method does not win.

## Positioning
- **Separated evidence, then fusion:** infrastructure and quality are scored by separate calibrated modules and combined by a rule frozen before the held-out evaluation, so an alert says *which kind* of problem it is and why, not only that something is anomalous. Existing detectors (fixed thresholds, Isolation Forest, One-Class SVM) are baselines, not the contribution.
- **Honesty as a feature:** every result states where its data came from (semi-synthetic vs real), test sets were read once under a logged lock, and losses are reported (Round 2: the frozen fusion rule did not beat simple threshold voting on the fresh test set by a detectable margin; Round 7: on real GECCO drinking-water data the refitted quality module found 4 of 12 events, fixed thresholds 11 of 12).
- **One bot, two directions:** the same Telegram bot pushes operator alerts and answers residents locally (open speech, translation and TTS models plus a small local LLM behind a grounding guard), without cloud APIs.

## Operating Context
- **Live demo / viva is the next real use** (user, 2026-10-18): laptop with the dashboard (`python scripts/run_demo.py --port 8200`), possibly a projector, a phone receiving the Telegram alert and talking to the citizen bot. Script: `docs/demo_script.md`.
- No physical hardware: virtual sensor nodes replay public data over a message bus as an ESP32 would. Fallback mode (one process, SQLite) by default; docker mode (MQTT + TimescaleDB, three processes) on request.
- The network is a **fictional 8-node layout near Vellore** (Ward N linked to sensor point node-N); tanker schedule, wards, notices and helpline are fictional demo data.
- Replay time differs from wall time (the replay runs at up to x1200); the operator can pause, change speed and inject test events.
- Paper screenshots (16, two themes, desktop 1440x900 and phone 390x844) are generated by `scripts/screenshots.py`.

## Capabilities and Constraints
- **Dashboard pages:** Overview (map with 8 sensor markers and citizen-report markers, status strip, live alert feed, replay controls), Node detail (four signal charts, evidence bars, "Why" explanation, node alerts), Alerts (filterable table), Complaints (citizen tickets with photo thumbnail, nearest sensor point, sensor state at report time), Method (what the system does and what the data are).
- **Node naming (Round 7):** every node shows its number and ward, e.g. "Bagayam Booster (node-4 · Ward 4)", short form "4 · Bagayam"; built only by `src/kami/live/labels.py` and `frontend/src/labels.ts`.
- **Statuses** are always colour + icon + text (colour-blind safe). Priority: Low, Medium, High, Critical. Category: Normal, Infrastructure, Quality, Combined.
- **Alert push:** Telegram, dry run by default; message under 600 characters, prefixed `[KAMI DEMO - simulated data]`, never names a cause.
- **Stack (existing):** React + TypeScript + Vite, Leaflet map (OpenStreetMap tiles need internet), FastAPI backend with WebSocket updates; Vitest and Playwright tests, axe-core scans.
- **Out of scope** (do not design for them): computer vision on photos, tanker routing, demand forecasting. Photos are stored for staff and never analysed automatically.
- **Required but not built yet: Hindi in the dashboard UI** (user, 2026-10-18). Today only the citizen bot speaks Hindi. Must be planned as a scoped round before it is built (CLAUDE.md scope rule).
- **Terminology:** "sensor point" or "node" (node-N), "ward", "model score" (one stream's calibrated evidence) vs "confidence" (the final fused value), "alert" vs "event" (an injected or labelled incident), "dry run".

## Brand Commitments
- Name: **KAMI**.
- Look **released for a full redesign** (user, 2026-10-18): the dark operations-console default and the old layout no longer bind. Still binding: every status as colour plus icon plus text; the **map as a core view**; a light/dark toggle; WCAG 2.1 AA; loading, empty and error states, keyboard focus, responsive layout; and it must **not look generic** (no admin template, no neon-on-black, no card grid).
- Data labels are part of the identity and must stay visible: "Demo network, fictional layout", "Simulated data", "semi-synthetic", "dry run", and `real` only for the GECCO test.

## Product Principles
1. **Operator speed over spectacle:** the first glance answers which node, what kind of problem, how urgent; everything else is one click away.
2. **Never overstate:** show what the sensors say, not a cause; label simulated, fictional and real data everywhere they appear; report uncertainty and losses plainly.
3. **The kind of problem matters:** infrastructure, quality and combined stay visibly distinct, because the separation is the method.
4. **Same truth in every channel:** dashboard, Telegram alert and citizen reply use the same node names, numbers and categories.
5. **Works for everyone in the room:** accessible by default, readable by an operator under time pressure, and (planned) usable in Hindi.

## Accessibility & Inclusion
- Required standard: **WCAG 2.1 AA** (user, 2026-10-18). Current automated evidence: axe-core scans of all pages in both themes, no serious or critical finding.
- Colour-blind safe statuses (colour + icon + text), visible keyboard focus, respects reduced motion, no horizontal scrolling at 390 px.
- Language: English dashboard today; **Hindi in the dashboard is required** (not built yet). Residents already use Hindi or English, text or voice, through the bot.
